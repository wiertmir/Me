# Tasks service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `tasks-service`, a REST API for task lists and tasks (subtasks, recurring tasks created on schedule), as a sibling of `calendar-service`.

**Architecture:** A new workspace crate that copies calendar-service's shape file for file: `lists.rs` is `calendars.rs`, `tasks.rs` is `events.rs` without overrides and ranges. What both services need (`Caller`, the time types, the rule builder) moves to `common` first. Recurrence has no timer: the extractor that identifies the caller also creates that user's due tasks, so every `/tasks/v1` route does it without knowing.

**Tech Stack:** Rust 2024, tokio, axum 0.8, rusqlite (bundled), utoipa, `rrule` 0.14, `chrono-tz` 0.10 — the versions in `calendar-service/Cargo.toml`.

**Spec:** `docs/superpowers/specs/2026-10-05-tasks-design.md`. Read it first; this plan does not repeat its rules, it says where each one goes.

## Global Constraints

- Mirror calendar-service: same error shape and codes, same `#[utoipa::path]` style (every handler documented with both security schemes and the `X-User-Id` header parameter), same test style (`TestApp`, real HTTP). When this plan says "as `calendars.rs`" or "as `events.rs`", copy that code's structure and change the names.
- API prefix `/tasks/v1`; port `8084`; database file `tasks.db`; environment prefix `ME_TASKS__`; log name `tasks-service`.
- Limits: 100 lists per user; 10,000 live tasks per list; name 1–100 chars; summary ≤ 500; description ≤ 10,000; uid 1–255; rrule ≤ 500; reminders ≤ 5, each 0–40,320; priority 0–9; years 1900–2200; at most 30 missed occurrences created per chain per catch-up.
- Someone else's list or task is 404 `not_found`, never 403.
- Task texts (summary, description) are never logged.
- No new dependencies beyond those calendar-service already has.
- Every timestamp the service writes comes from `AppState::now()`, never `Utc::now()` directly.
- After every task: `cargo test --workspace` and `cargo clippy --workspace --all-targets -- -D warnings` pass.

## Review Focus

Each line has its test in the task named.

1. **Two requests at once after a due date passes** must create one next task, not two (Task 7, `concurrent_requests_create_one_next_task`).
2. **A head whose due is far in the past** (daily from 1900) must answer promptly and create 31 tasks, not 46,000 (Task 7, `ancient_due_creates_thirty_and_the_head`).
3. **A rule whose next occurrence is after the year 2200** creates nothing and does not fail the request (Task 7, `next_occurrence_outside_the_year_window_ends_the_chain`).
4. **A stored rule that no longer parses** must not turn every request of that user into a 500; it is skipped with a warning (Task 7, `unreadable_stored_rule_is_skipped`).
5. **A list with room for the task but not its subtasks** creates nothing rather than half a copy (Task 7, `no_room_for_subtasks_creates_nothing`).

Decisions the spec leaves to here:
- **`due` form:** with `tz` it is `YYYY-MM-DDTHH:MM:SS` (`parse_when(_, false)`); without, `YYYY-MM-DD` (`parse_when(_, true)`). `tz` without `due` is 422.

- **`completed`:** open → completed sets `completed_at = s.now()`; completed → open clears it; otherwise unchanged. Creating with `completed: true` stamps it.
- **PUT and fixed fields:** `uid` and `parent_id`, when present in the body, must equal the stored values, else 422 `validation`. (Absent means unchanged, as in calendar.)
- **`rrule` in this task:** validated (`≤ 500` chars, `common::recur::validate` with the due as start; requires `due`) and stored. On create with a rule, and on PUT when the stored rule was null and the new one is not, `recurrence_id = id`; otherwise `recurrence_id` is unchanged. Nothing is created from it until Task 7.
- **`parent_id`:** in this task any non-null `parent_id` is 422; Task 5 lifts that.
- **Delete:** tombstone (`deleted = 1`, new revision), as events.
- Log events `task_created|updated|deleted` with `user_id`, `list_id`, `task_id`.

### Task 7: Recurrence

**Files:** Create `tasks-service/src/recurrence.rs`, `tests/recurrence.rs`. Modify `src/user.rs`, `src/lib.rs`.

**Interfaces:**
- Consumes: `tasks::{COLUMNS, from_row, bump, live_count, due_parts, subtasks, MAX_TASKS_PER_LIST}`, `common::recur::{build, wall}`.
- Produces:

```rust
/// Creates every task that is due for `user`'s chains at `now`. Never fails the request for a chain it
/// cannot read: that chain is skipped with a warning.
pub fn catch_up(c: &Connection, user: Uuid, now: DateTime<Utc>) -> rusqlite::Result<()>;
```

`User::from_request_parts` calls it after `Caller` succeeds: `s.db.with(|c| { let tx = c.unchecked_transaction()?; catch_up(&tx, user, s.now())?; tx.commit() })`.

**Algorithm**, per head (`rrule IS NOT NULL AND deleted = 0 AND due_utc <= now`, in the user's lists):

```
(start, tz, _) = due_parts(head.due, head.tz)
occ   = build(head.rrule, start, tz) as a lazy iterator of wall-clock When, in order
before = number of occ <= start            // 1 when the head's own due is an occurrence, else 0
later  = occ > start, with year in YEARS
take from `later` while its passed-instant <= now, then one more (the upcoming one) if there is one
keep  = the last 30 passed ones + the upcoming one
prev = head
for w in keep:
    kids = subtasks(prev)
    if live_count(list) + 1 + kids.len() > MAX_TASKS_PER_LIST: stop
    new = copy of head's summary, description, tz, priority, reminders, recurrence_id;
          due = w; open; id = uid = new uuid; rule = head's rule with COUNT rewritten (below)
    prev.rrule = NULL
    copy each of kids under new: open, new id and uid, same texts, due, tz, priority, reminders
    prev = new
```

- The passed-instant of a `When` is `due_parts`' third value: its instant for a time, 00:00 UTC of the next day for a date.
- **COUNT:** when the rule has a `COUNT`, the new task's rule carries as its `COUNT` the number of the original rule's occurrences at or after the new task's due (so `COUNT=3` becomes `COUNT=2` on the next task, and skipped occurrences are counted off too). Only the `COUNT=` part of the rule string is rewritten; `before` above exists for this sum.
- Every row written (new task, old head losing its rule, copied subtask) gets its own `bump` revision and `updated_at = now`.
- Log each created task at info: `event = "task_recurred"`, `user_id`, `list_id`, `task_id`, `follows` (the id of `prev`).
- A head whose rule or due does not parse: `tracing::warn!(event = "recurrence_skipped", task_id, …)` and continue with the next head.
- Mark with a `// ponytail:` comment that the iterator walks from the head's due to now on every request for a head that is not advanced (ended by `UNTIL`, or blocked by a full list), and that the fix is to clear the rule of an ended chain.
