# CalDAV bridge Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `caldav-bridge`, a stateless service that lets a CalDAV client (Thunderbird) read and write the calendars and task lists held by `calendar-service` and `tasks-service`.

**Architecture:** One axum handler takes every `/dav/*` request, signs the caller in with HTTP Basic against auth-service's verify endpoint, parses the path into a target (root, principal, home, collection, item) and dispatches on the method. A thin REST client talks to the two services with their service secrets; one module maps between their JSON and iCalendar; one writes the WebDAV XML. Nothing is stored: an item's address is its iCalendar UID, and the services gain a lookup by uid.

**Tech Stack:** Rust 2024, tokio, axum 0.8, reqwest, `common` (config, logging). New: `roxmltree = "0.21"` (read request XML), `icalendar = "0.17"` with its `parser` feature (read and write iCalendar).

**Spec:** `docs/superpowers/specs/2026-10-05-caldav-design.md`. Read it first; this plan says where each rule goes and does not repeat the mapping tables.

## Global Constraints

- Port `8085`; path prefix `/dav`; environment prefix `ME_CALDAV__`; log name `caldav-bridge`. No database, no `/api/*`, no OpenAPI.
- No dependencies beyond the workspace's existing ones plus `roxmltree` and `icalendar`.
- The bridge never logs the `Authorization` header, item names (uids) or item bodies. Paths are logged with the item name replaced.
- Request bodies are limited to 1 MB.
- A path naming another user answers 404. Unsupported methods answer 405.
- XML namespaces: `DAV:`, `urn:ietf:params:xml:ns:caldav`, `http://calendarserver.org/ns/` (`getctag`), `http://apple.com/ns/ical/` (`calendar-color`).
- Every commit message carries `Refs #16` (Task 1 also `Refs #25`) above the `Co-Authored-By` trailer.
- After every task: `cargo test --workspace` and `cargo clippy --workspace --all-targets -- -D warnings` pass.

## Review Focus

Each line has its test in the task named.

1. **A uid with characters that need encoding** (`a b/c@x%1`) must survive item name → uid → item name (Task 5, `uid_with_reserved_characters_round_trips`).
2. **Hostile or empty request XML:** a body with a `DOCTYPE` is 400, not a crash or an expansion; a `PROPFIND` with no body means "all properties" (Task 4, `doctype_is_refused`, `empty_propfind_body_lists_all_properties`).
3. **iCalendar text escaping and folding:** a summary with `,` `;` `\` and a newline, and a description longer than 75 octets, round-trip unchanged (Task 5, `text_escaping_and_long_lines_round_trip`).
4. **XML-special characters in an item** (`<`, `&`, `]]>` in a summary) inside `calendar-data` of a report are escaped and parse back (Task 5, `calendar_data_is_xml_escaped`).
5. **`RECURRENCE-ID` and `EXDATE` given in UTC** for a series stored with a zone must be read as that occurrence, not refused or shifted (Task 7, `utc_recurrence_id_matches_the_zoned_occurrence`).

`Signed`: decode `Authorization: Basic`, split at the first `:`, `POST {auth_url}/api/app-passwords/verify` with `X-Service-Secret: auth_secret`, `X-Forwarded-For` = the first address of the incoming `X-Forwarded-For` (absent when the request has none), body `{"username","password"}`. 200 → `Signed`. Missing or malformed header, or 401 → 401 with `WWW-Authenticate: Basic realm="Me"`. 429 → 429 with the same `Retry-After`. Anything else or unreachable → 503.

In this task every signed-in `/dav` request answers 204; later tasks replace that.

- Depth 1: Root → itself only; Principal → itself only; Home → itself and every collection; Collection → itself (items come in Task 5).

- Any other method → 405 (replacing Task 3's 204).


Decisions:
- An item's etag is the task's etag from the service, unchanged.
- `GET` an item: 200, `Content-Type: text/calendar; charset=utf-8`, `ETag`.
- `PUT`: the body's `UID` must equal the name (403 `valid-calendar-object-resource`). Look the uid up. `If-None-Match: *` with an existing task → 412. `If-Match` that differs from the stored etag, or is given for a task that does not exist → 412. Create → 201; replace → 204; both with the new `ETag`.
  - Create: `rrule` from the body's `RRULE` if any; `parent_id` from `related_to` when `task_by_uid` finds it in the same list and the service accepts it — on a 422 from the service because of the parent, create again without it.
  - Replace: `rrule` = the stored task's rule; `parent_id` omitted; everything else from the body.
- `DELETE`: honours `If-Match`; 204.
- `PROPFIND` depth 1 on a to-do collection and both reports use one `tasks(list)` call; parent uids come from the same listing. Multiget answers a 404 response for an href it does not have. `calendar-query` ignores its filter.
- `PRIORITY` 0–9 passes through; a value outside is stored as 0.
- Completed when `STATUS:COMPLETED`, a `COMPLETED` property, or `PERCENT-COMPLETE:100`.
- `RRULE` is never written by `todo_to_ical`.
- A body that is not exactly one `VTODO` (plus optional `VTIMEZONE`s) in a to-do collection → 403 `supported-calendar-data`.

### Task 6: events — single and all-day

**Files:** Modify `caldav-bridge/src/{backend,ical,dav}.rs`. Create `tests/events.rs`.

**Interfaces — Produces:**

```rust
// backend.rs — the calendar-service JSON
#[derive(Deserialize, Clone)] pub struct Event { pub id: Uuid, pub uid: String, pub summary: String, pub description: String,
    pub location: String, pub all_day: bool, pub start: String, pub end: String, pub tz: Option<String>,
    pub rrule: Option<String>, pub exdates: Vec<String>, pub reminders: Vec<u32>,
    pub recurring_event_id: Option<Uuid>, pub original_start: Option<String>, pub etag: String, pub updated_at: DateTime<Utc> }
#[derive(Serialize, Default, Clone, PartialEq)] pub struct EventWrite { /* the service's EventInput fields */ }
impl Backend<'_> {
    pub async fn events(&self, cal: Uuid) -> Result<(i64, Vec<Event>), DavError>;         // changes feed without since
    pub async fn events_by_uid(&self, cal: Uuid, uid: &str) -> Result<Vec<Event>, DavError>;  // series first
    pub async fn create_event(&self, cal: Uuid, e: &EventWrite) -> Result<Event, DavError>;
    pub async fn replace_event(&self, id: Uuid, e: &EventWrite) -> Result<Event, DavError>;
    pub async fn delete_event(&self, id: Uuid) -> Result<(), DavError>;
}

// ical.rs
pub struct ItemIn { pub uid: String, pub main: EventWrite, pub overrides: Vec<EventWrite> }   // overrides: Task 7
pub fn events_to_ical(parts: &[Event]) -> String;              // parts[0] is the single event or series
pub fn ical_to_events(body: &str) -> Result<ItemIn, DavError>;
pub fn item_etag(parts: &[Event]) -> String;                   // "\"{highest revision}-{number of parts}\""
```

Decisions:
- `item_etag`: each part's etag is its quoted revision; the item's is the highest revision and the number of parts. Every write in a calendar takes a new, higher revision, and removing a part changes the count, so the pair changes whenever a part is added, changed or removed.
- In this task a body with more than one `VEVENT`, or a `VEVENT` with `RECURRENCE-ID`, is refused with 403 `valid-calendar-data` ("not supported yet"); Task 7 lifts it. `RRULE` and `EXDATE` on the one `VEVENT` are read and written already here (they are plain fields).
- Reading times: the spec's rules. `DTSTART;VALUE=DATE` without `DTEND` and `DURATION` → `end` is the next day. `DURATION` is added to the start on the wall clock.
- `PUT`, `GET`, `DELETE`, preconditions, listing and reports exactly as for to-dos, with `item_etag` and events grouped by uid (a listing's overrides are grouped with their series by `uid`).
- `If-Match` is compared by the bridge against `item_etag` of what it just looked up; the service calls that follow are sent without it. Mark with a `// ponytail:` comment: two writers in the same instant can both pass; pass the series' etag through if that ever matters.

### Task 7: events — changed occurrences

**Files:** Modify `caldav-bridge/src/{ical,dav,backend}.rs`. Create `tests/series.rs`.

Lifts Task 6's refusal. A body may hold one `VEVENT` without `RECURRENCE-ID` (the series) and any number with it (overrides), all with the same `UID`.

Decisions:
- `RECURRENCE-ID` and `EXDATE` values are stored in the form of the series' `DTSTART`: a date for an all-day series; for a timed series the wall-clock time in the series' zone. A value given with `Z`, or with another `TZID`, is converted to the series' zone. `RANGE=THISANDFUTURE` is refused (403 `valid-calendar-data`).
- A body with overrides but no series part is refused (403).
- Write algorithm, in `dav.rs` or a function beside it:

```
stored  = events_by_uid(cal, uid)            // [] | [main, overrides…]
check preconditions against item_etag(stored)
main    = stored.is_empty() ? create_event(main) : replace_event(stored[0].id, main)   // replace only when it differs
for o in body.overrides:
    match stored override with the same original_start:
        some, differs → replace_event(id, o)      some, equal → nothing
        none          → create_event(o with recurring_event_id = main.id)
for stored overrides whose original_start is not in the body: delete_event(id)
answer with item_etag(events_by_uid(cal, uid))
```

  "Differs" compares the `EventWrite` built from the body with one built from the stored event, so an unchanged part costs no write and keeps its revision.
- The first failing call ends the write with that error; nothing is rolled back.
- `events_to_ical` writes the series, then each override with its `RECURRENCE-ID` (`TZID` form for timed, `VALUE=DATE` for all-day).
