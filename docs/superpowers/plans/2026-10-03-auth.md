# Me Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `auth-service` (Rust), `auth-web` (Blazor Server) and the `common` crate so users can sign up, sign in (password or Google/GitHub/Microsoft) and obtain OAuth 2 / OpenID Connect tokens.

**Architecture:** auth-service owns all data and security decisions and exposes an internal JSON API (`/api/*`, service secret) plus public OAuth and social endpoints. auth-web is a stateless Blazor Server UI that calls the internal API and holds the session token in an encrypted cookie. `common` gives later services token verification and the shared error type.

**Tech Stack:** Rust 1.96 (edition 2024), tokio, axum, rusqlite (bundled), argon2, jsonwebtoken, p256, oauth2, reqwest, lettre, tracing, utoipa + utoipa-axum + utoipa-scalar. .NET 10 Blazor Web App (Server interactivity), NLog.Web.AspNetCore.

**Spec:** `docs/superpowers/specs/2026-10-03-auth-design.md`

## Global Constraints

- Add dependencies with `cargo add` / `dotnet add package` (latest stable); check current API with the context7 docs tool before using utoipa-axum, oauth2, jsonwebtoken and lettre.
- Passwords: Argon2id, minimum 12 characters, maximum 1024 bytes, no composition rules.
- Every secret token (session, refresh, auth code, email token, app password, social ticket) is 32 random bytes, base64url, stored as SHA-256 hex. Never logged.
- Lifetimes: session 30 days; auth request 10 minutes; auth code 60 seconds; access token 15 minutes; refresh token 30 days; email-verify token 24 hours; reset token 1 hour; social ticket 60 seconds.
- Usernames and emails are trimmed and compared case-insensitively (stored lower-case). Username: 3–32 chars of `a-z 0-9 . _ -`.
- Every `/api/*` route except `/api/openapi.json` and `/api/docs` requires header `X-Service-Secret`; user-scoped routes also require `Authorization: Bearer <session token>`.
- Errors: JSON `{"code": "...", "message": "..."}` via `common::ApiError`. OAuth endpoints use RFC 6749 error JSON (`error`, `error_description`).
- Every handler is registered through `utoipa_axum::routes!` with a `#[utoipa::path]` annotation; every request/response type derives `ToSchema`.
- Logging: `tracing` events with fields, never interpolated strings. Security events (listed in the spec) at info/warn. C#: NLog message templates.
- Each handler file stays focused on one area; database access goes through functions in the owning module, not inline SQL in handlers.
- Commit after each task with the trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Redirect URI that is not an exact match of a configured one** → `/oauth/authorize` shows an error and never redirects to it (Task 5).
2. **Username/email with different case or surrounding spaces** (`" Wiertmir "`) → signs in as the same user; sign-up with it is a conflict (Task 2, Task 3).
3. **Replayed or expired one-time values** (auth code used twice, expired challenge, reset link used twice) → rejected; a replayed auth code also revokes the tokens it issued (Task 3, Task 5).
4. **auth-service unreachable from auth-web** → a friendly "service unavailable" page, no stack trace, logged once at error (Task 10).
5. **Tampered `returnUrl` on auth-web sign-in** (`//evil.example`, absolute URLs) → ignored, user lands on `/account` (Task 10).

Public routes: `GET /oauth/authorize` (params `response_type=code, client_id, redirect_uri, scope, state, code_challenge, code_challenge_method=S256, nonce?`); `POST /oauth/token` (form-encoded; grants `authorization_code` with `code_verifier`, and `refresh_token`); `GET /oauth/userinfo` (bearer access token); `POST /oauth/revoke`; `GET /.well-known/openid-configuration`; `GET /.well-known/jwks.json`. Internal: `GET /api/auth-requests/{challenge}` → `{client_id, client_name, scope}`; `POST /api/auth-requests/{challenge}/accept` (SessionUser) → `{redirect_to}`.

Rules: unknown client or non-exact `redirect_uri` → 400 HTML error page, no redirect. Other invalid parameters → redirect to the client with `error=invalid_request&state=…`. Valid → 302 to `{web_url}/signin?challenge=<id>`. For loopback redirect URIs (`http://127.0.0.1` / `http://localhost`) the port is ignored when matching (RFC 8252). An auth code presented twice → `invalid_grant` and its refresh-token family is revoked. Refresh rotation: each use marks the token used and issues a new one in the same family; presenting a used token revokes the family.

**Interfaces — Produces:**

```csharp
public sealed class AuthApi(HttpClient http) {            // typed client; BaseAddress = AuthService:BaseUrl
    Task<ApiResult<SignInResponse>> SignIn(string login, string password);
    Task<ApiResult> SignOut(string session);
    Task<ApiResult> ChangePassword(string session, string current, string @new);
    Task<ApiResult<User>> Me(string session);
    Task<ApiResult<AcceptResponse>> AcceptAuthRequest(string session, string challenge);
    // later tasks add methods in the same style
}
public record ApiResult(bool Ok, string? Code, string? Message);   // generic variant carries Value
public static class SessionPrincipal {                              // cookie auth helpers
    Task SignIn(HttpContext ctx, string sessionToken, User user);   // claims: session, sub, name, role=admin, must_change
    string? Token(ClaimsPrincipal user);
}
```

Decisions:
- ASP.NET cookie authentication (cookie `me_auth`, HttpOnly, Secure, SameSite=Lax, 30 days); data-protection keys persisted to `DataProtection:Path`.
- A `DelegatingHandler` adds `X-Service-Secret`, `X-Request-Id`, `X-Forwarded-For` and `X-Client-User-Agent` to every call. Middleware creates the request id and pushes it into NLog's `ScopeContext`.
- NLog is the only logging provider (`builder.Logging.ClearProviders(); builder.Host.UseNLog();`). `nlog.config` has a coloured console target and a JSON console target, switched by the `LOG_FORMAT` variable. Log with templates: `logger.LogWarning("Sign-in failed for {Login}: {Code}", …)`.
- Sign-in, change-password and sign-out are static SSR pages (`[ExcludeFromInteractiveRouting]`, `<form method="post" @formname>` with `<AntiforgeryToken />`, `[SupplyParameterFromForm]`). Account is `@rendermode InteractiveServer` with `[Authorize]`.
- A principal with `must_change` is redirected to `/change-password` from every other page (middleware). After a successful change the cookie is re-issued.
- `/signin?challenge=X`: if already signed in, accept immediately; otherwise accept after sign-in; redirect to `redirect_to`. `/signin?returnUrl=…` is honoured only when it is a local path (`Url.IsLocalUrl` semantics); otherwise go to `/account`.
- API unreachable (`HttpRequestException`/timeout) → `ApiResult` code `unavailable`, logged at error, page `/unavailable`. API 401 on a user call → sign the cookie out and redirect to `/signin`.
- Markup is semantic and unstyled beyond layout in this task; Task 13 does the visual design.
