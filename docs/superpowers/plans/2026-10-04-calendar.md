# Calendar Service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Rust REST API, `calendar-service`, that stores each user's calendars and events, expands recurrence for a date range and offers a changes feed.

**Architecture:** A new workspace crate beside `auth-service`, with its own SQLite file. Code both services need (logging, extractors, config loading, service-secret rules, the SQLite wrapper) moves into `common` first. Callers are identified by a bearer access token or by the service secret plus `X-User-Id`.

**Tech Stack:** tokio, axum 0.8, rusqlite (bundled), serde, utoipa / utoipa-axum, tracing, chrono; new: `rrule` 0.14, `chrono-tz` 0.10.

**Spec:** `docs/superpowers/specs/2026-10-04-calendar-design.md`

## Global Constraints

- Listen address `127.0.0.1:8083`; database file `<data_dir>/calendar.db`; env prefix `ME_CALENDAR__`.
- All API routes under `/calendar/v1`; `/health`, `/api/openapi.json`, `/api/docs` outside it.
- Errors are `common::ApiError` (`{code, message}`) with the codes of the spec's error table.
- Someone else's calendar or event answers 404 `not_found`, never 403.
- Every SQL statement on `calendars` or `events` is filtered by the caller's user id (events through their calendar).
- Summary, description and location are never logged.
- Limits: name 1–100 chars; colour `#rrggbb`; summary 500; location 500; description 10,000; `rrule` 500; `exdates` 1,000 entries; `reminders` 5 entries, each 0–40,320; 100 calendars per user; range ≤ 366 days; ≤ 5,000 occurrences per answer.
- Follow auth-service's idiom: `utoipa::path` on every handler, `OpenApiRouter`, `ApiJson` / `PathId` extractors, comments at the density of the surrounding code.
- No new dependency beyond `rrule` and `chrono-tz`.
- Commit after each task with the repository's attribution trailer.

## Review Focus

Inputs the spec implies and no feature test would otherwise exercise; each has a test in the task named.

1. A timed event whose start falls in a daylight-saving gap (`2027-03-28T02:30:00`, `Europe/Warsaw`) is accepted and placed at `01:30:00Z` — Task 5.
2. A daily series that began twenty years ago, queried for one week, returns that week's seven occurrences and is neither slow nor refused by the cap — Task 6.
3. A monthly series starting on the 31st skips months without a 31st instead of failing or drifting — Task 6.
4. `from=2026-10-05T00:00:00+02:00` sent without URL-encoding (the `+` arrives as a space) answers 422 `validation`, not 500 — Task 6.
5. A timed event that starts before `from` and ends after it (crossing the range boundary, or midnight) is included — Task 6.

pub fn parse_when(s: &str, all_day: bool) -> ApiResult<When>;

pub fn parse_tz(s: &str) -> ApiResult<Tz>;                        // chrono_tz::Tz; Err = 422 `validation`
/// Wall-clock time in `tz` as an instant. A skipped time moves forward by the gap; a repeated one takes the earlier.

impl When { /// Dates are midnight in `tz`.
            pub fn instant(self, tz: Tz) -> DateTime<Utc>; }

// recur.rs
/// 422 `validation` unless the rule parses for this start and its FREQ is DAILY, WEEKLY, MONTHLY or YEARLY.
pub fn validate(rrule: &str, start: When, tz: Tz) -> ApiResult<()>;
/// Starts of the occurrences whose [start, start + duration) overlaps [from, to), in order, `exdates` removed.
/// `tz` is the event's zone, or the query zone for an all-day series. More than `limit` results:
/// Err 422 `too_many_occurrences`.
pub fn starts(rrule: &str, start: When, duration: chrono::Duration, exdates: &[When], tz: Tz,
              from: DateTime<Utc>, to: DateTime<Utc>, limit: usize) -> ApiResult<Vec<When>>;
/// Whether `at` is the start of an occurrence of the series (and not in `exdates`).
pub fn is_occurrence(rrule: &str, start: When, exdates: &[When], tz: Tz, at: When) -> bool;

`to_utc` for a skipped time: take the UTC offset in force three hours earlier (`tz.offset_from_local_datetime(&(local - 3h))`, earliest) and subtract it from `local`.

Read `cargo doc -p rrule --open` for the exact names in 0.14 before writing; the tests below are the contract, not this paragraph.

Decisions:
- `etag` is `"\"{revision}\""` (quoted, as the `ETag` header requires). Every write runs in one transaction: `UPDATE calendars SET sync_token = sync_token + 1 … RETURNING sync_token`, and the event row takes that value as `revision`.
- Derived instants: `start_utc`/`end_utc` are `When::instant` in the event's zone; all-day events use UTC (Task 6 widens its query to compensate). For a series `end_utc` is NULL. *(The spec's "end of its last occurrence" is replaced by NULL: every series of the calendar is expanded per query. Mark it `// ponytail:` with that ceiling.)*
- Validation (422 `validation`): the Global Constraints limits; timed needs `tz`, all-day must not have one; `end` after `start`; `rrule` through `recur::validate`; each `exdates` entry parses in the event's form; `uid` 1–255 chars.
- Override: `recurring_event_id` and `original_start` come together; the series must exist, not be deleted, be in the same calendar, have an `rrule` (else 422); an override has no `rrule` and no `exdates` (422); its `uid` is the series' uid; `all_day` equals the series'. A second override for the same occurrence: 409 `conflict`. A used `uid`: 409 `conflict`.
- `PUT`: body is `EventInput`. `uid`, `recurring_event_id`, `original_start` may be omitted; when given they must equal the stored values, else 422.
- `If-Match` on `PUT` and `DELETE`: compared as a string with the current `etag`; unequal → 412 `etag_mismatch`. Absent → proceed.
- `DELETE` sets `deleted = 1` and the new revision on the event and, for a series, on its overrides. A deleted event answers 404 everywhere except the changes feed.
- `POST` answers 201; `POST`, `GET` and `PUT` send the `ETag` header; `DELETE` answers 204.

Routes: `POST /calendar/v1/calendars/{id}/events`; `GET, PUT, DELETE /calendar/v1/events/{id}`.

### Task 6: Range query

**Files:**
- Modify: `calendar-service/src/events.rs`, `tests/openapi.rs`
- Create: `tests/recurrence.rs`

**Interfaces:**
- Consumes: `recur::starts`, `recur::is_occurrence`, `events::from_row`.
- Produces: `GET /calendar/v1/calendars/{id}/events?from=&to=&tz=` → `Vec<Occurrence>`:

```rust
pub struct Occurrence { #[serde(flatten)] event: Event,      // start, end, original_start overwritten per occurrence
                        start_utc: DateTime<Utc>, end_utc: DateTime<Utc> }
```

Algorithm:
1. Parse `from`, `to` (RFC 3339 with offset), `tz` (default `UTC`). 422 `validation` when missing, unparsable, `to <= from`, or more than 366 days apart.
2. Load the calendar's non-deleted rows that are a series (`rrule IS NOT NULL`, `start_utc < to + 14h`) or have `start_utc < to + 14h AND end_utc > from - 14h`. The 14 hours cover all-day rows, whose stored instants assume UTC.
3. Single events and overrides: compute exact instants (all-day in the query `tz`), keep those overlapping `[from, to)`. An override is kept only when `recur::is_occurrence` holds for its series and `original_start`.
4. Each series: `recur::starts` with the remaining budget of the 5,000 cap; drop starts that an effective override replaces; each start becomes an `Occurrence` with `end = start + (series.end - series.start)` and `original_start = start`.
5. A single event's `original_start` is null; an override's is its stored value. Sort by `start_utc`, then `id`. More than 5,000 in total → 422 `too_many_occurrences`.
